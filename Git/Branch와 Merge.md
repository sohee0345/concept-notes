# Branch와 Merge

## 1. 개념

Branch는 여러 개발자가 서로 다른 작업을 동시에 진행할 수 있도록 작업 흐름을 분리하는 기능이고, Merge는 분리된 작업 내용을 하나로 합치는 과정이다.

> **핵심:** 안정된 코드와 개발 중인 코드를 Branch로 분리하고, 완료된 작업만 Merge하여 통합한다.

------------------------------------------------------------------------

## 2. 쉽게 이해하기

``` text
공통 출발점
  ├─ feature A에서 기능 개발
  └─ feature B에서 기능 개발
          ↓
      Merge로 통합
```

> **쉽게 말하면:** 같은 문서의 복사본에서 각자 작업한 뒤 완성된 내용을 원본 흐름에 합치는 것과 비슷하다.

------------------------------------------------------------------------

## 3. 사용 방법

| 브랜치 | 역할 |
| --- | --- |
| `main` | 서비스 배포에 사용하는 안정된 코드 관리 |
| `develop` | 개발 기능을 통합하고 테스트 |
| `feature` | 기능별 개발 작업 |
| `release` | 배포 전 실제 데이터로 QA와 테스트 |
| `hotfix` | 운영 중 발생한 오류를 빠르게 수정 |

``` text
main → develop → feature
                   ↓ 개발 완료 후 Merge
                develop → release → main
```

운영 중 오류가 발생한 경우:

``` text
main → hotfix → 수정 → Merge
```

> **핵심:** 수업 흐름에서는 develop을 main에서 만들고, feature를 develop에서 만든다.

### Branch Protection Rule

GitHub 저장소의 `Settings → Branches`에서 중요한 브랜치에 보호 규칙을 적용할 수 있다. 수업에서는 `Branch name pattern`에 `main`을 지정했다.

``` text
main 브랜치 보호
  ↓
dev 브랜치에서 개발 내용 통합
  ↓
Pull Request 생성
  ↓
승인 후 main에 Merge
```

실습 화면에서는 다음 설정을 확인했다.

- Merge 전에 Pull Request 요구
- Pull Request 승인 요구
- 보호 규칙의 우회 금지

> **핵심:** 안정된 `main`에 직접 변경을 반영하기보다 Pull Request와 승인을 거치도록 보호한다.

## 4. 예제

``` text
develop 브랜치 선택
  ↓
새 feature 브랜치 생성
  ↓
feature에서 기능 개발
  ↓
develop 브랜치에서 Branch → Merge
  ↓
개발이 끝난 feature 브랜치 삭제
```

### 코드 해석

- `Branch` → 독립된 작업 흐름을 만든다.
- `Merge` → 선택한 Branch의 변경 내용을 현재 Branch에 합친다.
- `origin` → GitHub 원격 저장소를 가리키는 기본 이름이다.

> **결과 해석:** feature의 개발 내용이 develop에 통합되고, 완료된 feature 브랜치는 삭제할 수 있다.

------------------------------------------------------------------------

## 5. 헷갈리는 개념 비교

| 구분 | Branch | Merge | Branch Protection |
| --- | --- | --- | --- |
| 의미 | 작업 흐름 분리 | 분리된 작업 통합 | 중요한 브랜치 보호 |
| 사용 시점 | 새 기능이나 수정 시작 전 | 작업이 완료된 후 | 저장소 운영 규칙 설정 시 |
| 결과 | 독립된 작업 공간 생성 | 대상 Branch에 변경 내용 반영 | 승인·PR 등의 조건 적용 |

------------------------------------------------------------------------

## 6. 주의할 점

- 새 Branch를 만들 때 어떤 Branch를 기준으로 만드는지 확인한다.
- 수업 흐름에서는 완료된 feature 브랜치를 삭제하고 `develop`, `main`을 남긴다.
- Merge할 때 현재 Branch와 합칠 대상 Branch를 구분한다.
- 보호 규칙의 `Branch name pattern`이 실제 보호할 브랜치 이름과 일치하는지 확인한다.
- Pull Request 승인 조건이 있다면 필요한 승인 수를 충족한 뒤 Merge한다.

## 🟦 핵심 정리

### 💡 주요 개념

| 개념 | 의미 |
| --- | --- |
| `Branch` | 독립된 작업 흐름 |
| `Merge` | Branch의 변경 내용을 합치는 과정 |
| `origin` | GitHub 원격 저장소의 기본 이름 |
| `Branch Protection` | 중요한 브랜치의 변경과 병합 조건을 설정하는 규칙 |
| `Pull Request` | 다른 브랜치의 변경을 검토하고 병합하도록 요청하는 과정 |

### ⭐ 한 줄 정리

> **Branch로 개발 작업을 분리하고 Pull Request와 보호 규칙을 거쳐 안정된 main에 Merge한다.**
